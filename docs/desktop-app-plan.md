# Proxira 桌面版技术方案

> 目标平台：macOS　|　桌面壳：Electron　|　用途：**本机自用，不做对外分发**
>
> **已锁定决策**
> 1. 拦截深度 = 系统代理 + HTTPS MITM
> 2. 桌面壳 = Electron（Tauri 需 Rust 工具链，排除）
> 3. 平台 = macOS 优先
> 4. 不开通 Apple Developer 账号，仅在本机使用
> 5. 根 CA 装入 System keychain，使用时提示提权
> 6. v1 只支持 HTTP/1.1，不做 h2 协商
> 7. 技术栈 = Node 复用（内核与采集层都用 Node，不换 Go / Rust，理由见 §2.7）
> 8. 能力边界 = 不做 UDP 拦截 / 不做裸 TCP·UDP 内容解析 / 不做「只拦某个 App」/ 不解密证书固定的 App（见 §1「明确不做」与 §5.7）
>
> **待确认**：仓库布局（本文 §2 给出建议）、是否启动 Phase 0 spike

---

## 1. 目标与范围

把 Proxira 从「按前缀拦截的本地代理」升级为**桌面窗体应用**，能拦截整台 Mac 上的网络请求，并对 **HTTPS 内容做解密观测**。

**验收标准（一句话）**：在本机启动桌面应用、打开拦截开关后，浏览器和终端里发生的 HTTP 与 HTTPS 请求，都能在面板里看到完整明文。

### 明确不做（避免投入无底洞）

| 想做的事 | 为什么不做 |
|---|---|
| 看**裸 TCP / UDP 的内容** | 需要为每个协议写解析器，工作量无边界。要看包内容请用 Wireshark |
| 拦截 **UDP**（DNS / QUIC） | 系统代理基于 TCP，UDP 完全不经过；要拦 UDP 必须上 Network Extension，而无 Apple 账号拿不到该 entitlement |
| **只拦**某个 App（作用域） | 系统代理是全局开关。正确模型是「全机接管 + 内部按 PID 分流」 |
| 解密**证书固定**的 App（微信、各类私有协议） | 微信用 MMTLS + 预置 ECDSA 公钥校验服务端，**装任何根 CA 都无法冒充**，密码学死路。详见 §5.7.5 |
| 用 `pf` 做**按进程**重定向 | macOS 的 `pf` 无法按 PID 匹配；且 `rdr` 转换规则**连 user / group 都不能匹配**，DNS 还会走 `_mdnsresponder` 导致归属错乱 |

### 前提：这是自用工具

这一条会砍掉大量工作，必须写清楚：

| 因为自用，所以不需要 | 省掉的成本 |
|---|---|
| Apple Developer 账号与代码签名 | 无需 $99/年，无需处理证书链 |
| 公证（notarization） | 无需走 Apple 的提交审核流程 |
| Gatekeeper 通过性 | 首次打开右键/`xattr` 绕过即可，只有自己受一次影响 |
| 自动更新框架 | 手动重装即可 |
| 跨平台抽象 | 只写 macOS 分支，不做平台适配层 |
| 安装器体验打磨 | 能双击启动就行 |

**反过来，自用反而让两件事更严格**：一是「崩溃残留系统代理」会把自己的机器搞断网，必须做兜底；二是根 CA 装进 System keychain 后对全机生效，卸载路径必须可靠。

## 2. 仓库布局与边界

### 2.1 问题的实质

桌面版看起来「多了很多功能」，但把需求拆开看，**大部分不是新功能，只是同一个内核换了个入口**：

| 你提到的桌面版需求 | 现状 | 是否为新内容 |
|---|---|---|
| 拦截本机的所有网络 | 代理内核已具备，只是入口从前缀变成系统代理 | 入口是新的，内核不是 |
| 做出记录 | 已有 history / runtime-store / 面板 | **不是** |
| 启动软件后开启拦截 | 桌面壳的职责（开关 / 托盘 / 生命周期） | 是新的，但是壳的活 |
| 看 HTTPS 明文 | 无 | **是唯一真正的新内核能力** |

### 2.2 代码量对比

| 部分 | 规模 | 归属 |
|---|---|---|
| `apps/getway/src`（代理内核 / 规则 / 重放 / 脱敏 / API / CLI） | 4863 行产品代码 + 131 行内联测试 = 4994 行 / 24 文件 | 复用 |
| `apps/dashboard/src`（面板，仅通过 11 个 HTTP 接口与后端耦合） | 5459 行 TS/Vue + 1494 行 CSS = 6953 行 / 18 文件 | 复用 |
| `packages/core/src`（共享类型） | 143 行 | 复用 |
| **小计（已有、且已测）** | **约 12090 行 / 102 个测试**（测试全部在后端） | — |
| 桌面层（MITM 引擎 + 系统代理 + 根 CA + Electron 壳 + 面板增量） | **约 2000~3000 行** | 新增 |

**复用 : 新增 ≈ 8 : 2**。一个 80% 复用既有代码的应用，不适合独立成仓。

### 2.3 耦合是真实且高频的

- 桌面版**内嵌** `apps/getway`，面板由 `apps/dashboard` 产出，`packages/core` 是两端共享类型
- 改一行规则匹配逻辑、改一个面板组件，桌面版就得一起重建
- 桌面版反过来会**推动核心演进**：MITM 之后规则匹配要从「路径包含」扩展到「路径 + host」，这是同时改核心和桌面的改动

如果拆成两个仓库，每次这类改动都要「改 A 仓 → bump 版本 → 改 B 仓依赖 → 重建」，版本漂移会变成长期 bug 源。**在耦合最紧的阶段分仓，等于自己给自己上枷锁。**

### 2.4 结论与边界设计

**建议：留在同一个仓库，但新增一个边界明确的私有包 `apps/desktop`。**

```
apps/getway       →  npm proxira（发布）   代理内核 + API + CLI
apps/dashboard    →  面板构建产物
packages/core     →  共享类型
apps/desktop      →  private: true（不发布）  MITM 引擎 / 系统代理 / 根 CA / Electron 壳 / 打包
```

**这样能同时满足两边的要求：**

- 桌面版能直接复用 12090 行既有代码，一处修改一处生效
- `proxira` 这个 npm 包**完全不受污染**：它的 `files` 白名单已经只有 `dist` 与 `dashboard-dist`，运行依赖只有 hono / zod / chalk / boxen，**Electron 与特权代码永远不会进入发布产物**
- 桌面版的「拦整机流量 + 要提权 + 装根 CA」这些**信任画像完全不同**的代码，待在 `apps/desktop` 里，与公开的开发者工具在物理上分开放

### 2.5 「换工具构建」和「拆仓库」是两回事

这两件事经常被混在一起，其实是正交的：

| 维度 | 建议 | 说明 |
|---|---|---|
| 仓库布局 | **同仓** | 依据是复用率与耦合度 |
| 桌面版构建工具 | **换成 `electron-vite`**（或 Electron Forge） | 桌面版有自己的构建需求（主进程/预加载/渲染进程三段产物），用专用工具比手搓 Vite 配置省事 |

也就是说：**换构建工具是对的，但它不构成拆仓的理由。**

### 2.6 什么情况下我会改口建议拆仓

- 桌面版要**独立对外发布或授权**（那是另一个产品，不是自用工具的升级）
- 你**不希望桌面版代码公开**（当前仓库是 public；公开可见 ≠ 发布到 npm，但确实会被看到）
- 桌面版要换成**完全不同的语言栈**（例如用 Go/Rust 重写代理内核）→ **已评估并否决，见 §2.7**
- 有**其他人**只维护桌面版，不需要看到内核

以上四条目前都不成立。（第二条已在 2026-09-16 澄清：仓库本就是开源的，别人 clone 下来自己编译即可，不构成拆仓理由。）

### 2.7 为什么内核继续用 Node，不换 Go / Rust

#### 先分清「换语言」指的是哪一层

| 层 | 内容 | 规模 | 与语言的关系 |
|---|---|---|---|
| 面板 | Vue + CSS | 6953 行 | **无关**。后端换什么语言，面板都还是 WebView 里的 HTML/CSS/JS |
| 业务内核 | 规则 / 重放 / 脱敏 / 历史 / SSE / 分组路由 / API | 4994 行 + 102 个测试 | **强相关**。换语言 = 全部重写 |
| 采集引擎 | CONNECT + 动态签发 + 根 CA + 系统代理开关 | 新增 2000~3000 行 | **无关**。三种语言做法一一对应，概念完全一样 |

所以「用 Go/Rust 重写」的真实含义是：**重写中间那 4994 行 + 102 个测试**。而新写的采集层本来就不在讨论范围内——它用什么语言写都一样。

#### 换语言能换来什么

| 收益 | 对自用工具是否成立 |
|---|---|
| 单文件二进制，不用带运行时 | **不成立**——你仍然需要 Electron 或 Tauri 做窗口，运行时省不掉 |
| 内存占用（Node/Electron ≈ 200MB，Go ≈ 20MB，Rust ≈ 10MB） | 成立，但自用工具不是常驻服务，200MB 无关痛痒 |
| 吞吐 / 延迟 | **不成立**——个人流量几十 rps，Node 绰绰有余 |
| 交叉编译 / 分发包更小 | 自用 + 不跨平台，不成立 |
| **MITM 生态有现成实现** | **成立**——唯一真正的收益，见下表 |

#### MITM 生态与许可证

| 语言 | 库 | 许可证 | 可用性 |
|---|---|---|---|
| Go | `AdguardTeam/gomitmproxy` | **GPL-3.0** | ❌ **陷阱**：这是搜「Go MITM」最显眼的结果，copyleft 会传染，MIT 项目不能引 |
| Go | `lqqyt2423/go-mitmproxy` | MIT | ✅ 可用。自带按域名签发的证书缓存、addon 机制，证书路径兼容 mitmproxy |
| Go | `google/martian` | Apache-2.0 | ✅ 可用。Google 出品，偏底层 |
| Go | `elazarl/goproxy` | MIT | ⚠️ 是「HTTP 代理库」不是「MITM 库」，签发自签证书要自己写 |
| Rust | `hudsucker` | MIT/Apache-2.0 | ✅ 可用。`rcgen` 纯 Rust 签发，月下载 10 万+，**并且自带 HTTP/2** |

> ⚠️ **许可证陷阱值得单独记一笔**：真动手搜 Go 方案时，第一个撞上的多半是 `AdguardTeam/gomitmproxy`，它是 **GPL-3.0**。引进 GPL 依赖会把整个仓库拖成 GPL，mit 协议作废。这条要在写第一行代码之前就知道。

> 顺带一提：Rust 的 `hudsucker` 自带 HTTP/2 支持，**换成 Rust 的话，「v1 只支持 HTTP/1.1」这条让步可以取消**。这是换语言唯一一个能实质提升产品能力的点，也是最值得拿来权衡的筹码。

#### 但 Node 自己做这件事并不难

MITM 内核在三个语言里的关键 API 是一一对应的，Node 的写法并不比 Go/Rust 长：

| 环节 | Node | Go | Rust |
|---|---|---|---|
| 接管 CONNECT | `http.createServer` 的 `'connect'` 事件 | `http.Hijacker` | `hyper` upgrade |
| 按 SNI 取证书 | `tls.createServer({ SNICallback })` | `tls.Config.GetCertificate` | `ServerConfig::cert_resolver` |
| 用 CA 签叶证书 | `selfsigned` / `node-forge` | `crypto/x509.CreateCertificate` | `rcgen` |

**MITM 内核本身不是「Node 做不了」的事**——按 §4 决定二，它只是一个三五百行的独立中间件。为了这三五百行去重写另外 4994 行，账算不过来。

#### 第二个成本：跨语言的类型共享会断裂

`packages/core` 的 143 行是前后端共享的 TypeScript 类型。内核一旦换 Go/Rust：

- `@proxira/core` 用不上，得在 Go 侧手写一份 `struct` 镜像，Rust 侧再写一份
- 每加一个字段要改三处，且**没有任何编译器帮你查漏**

这比 §2.3 说的跨仓版本漂移更糟——后者至少还有 TS 编译期兜底，前者是完全手动的。

#### 结论

**内核和采集层都用 Node 写，不换 Go / Rust。** 理由按权重排序：

1. 复用 12090 行已测代码（面板 6953 + 内核 4994 + 类型 143）。换语言等于把其中 5137 行连 102 个测试一起丢掉
2. 换来的主要是「内存小一点」，对自用工具无意义
3. MITM 内核是三五百行中间件，不是换语言的理由
4. 唯一成立的两条收益——Rust 的 HTTP/2、单文件二进制——在「不跨平台 / 不对外分发」的前提下都不值 5000 行重写

#### 但要把「将来能换」设计进去（这件事成本为零）

现在就该守的一条边界：**别让内核和采集层长得像同一层代码。**

- 采集层只做一件事：把 TLS 流变成 Web 标准 `Request`，喂给 `app.fetch`
- 采集层**不 import** `ProxyService` / `RuntimeStore` / 规则引擎的任何内部符号
- 采集层与内核之间只有「Web 标准 Request / Response」这一种数据类型

这条边界今天不花任何代价，但它意味着：**将来真要把采集层换成 Go/Rust，换掉的是一个千行左右的进程，内核和面板一行不动。** 这才是「保留选择权」的正确做法——而不是现在就把选择权兑现成 5000 行重写。

反过来说：**这条边界也正是 §2.6 第四条（换语言导致拆仓）成立的前提**。只有采集层真的换了语言，拆仓才有依据。

## 3. 现状盘点

### 3.1 已有、可直接复用

| 能力 | 位置 | 对桌面版的意义 |
|---|---|---|
| 代理内核 | `apps/getway/src/proxy/service.ts` | 上游转发、超时、504/502 已就绪 |
| 应用装配 | `apps/getway/src/app/create-app.ts` | `app.fetch` 是**纯 Web 标准 handler**，可直接跑在 Electron 主进程，**零改动** |
| 面板 | `apps/dashboard` → `DashboardAssets` 从磁盘发 | 构建产物可直接托管 |
| 规则 / 重放 / 脱敏 | `rules/`、`/api/replay`、`utils/redact.ts` | 只依赖 `Request`/`Response`，**transport 无关**（`test/https-proxy.test.ts` 已断言）→ MITM 后自动生效 |
| 数据目录 + 实例锁 | `config/data-dir.ts` | 用户级默认路径 + `instance.json` 防多开 |
| 自签证书生成 | `proxira gen-cert` | 证书工具链的起点 |

### 3.2 缺口（全部为零）

| 缺口 | 说明 |
|---|---|
| 无 CONNECT 处理 | 源码里没有任何 `connect` 事件监听，也没有 `http.createServer` 的 CONNECT 分支 |
| 无根 CA | `gen-cert` 生成的是**自签叶证书**（给自己套 TLS 用），缺 `basicConstraints: CA:true` / `keyCertSign`，**不能签发下级证书** |
| 无动态签发 | 没有按域名生成叶证书、没有证书缓存、没有 `SNICallback` |
| 无系统代理开关 | 没有 `networksetup` 调用，也没有还原逻辑 |
| 无桌面壳 / 托盘 / 打包 | — |
| **端口策略与桌面版冲突** | `index.ts` 的 `askForPort()` 用 readline 交互；GUI 下没有 TTY，会静默走「系统分配随机端口」分支。而**系统代理必须指向固定端口**——这条路径在桌面版下是坏的，必须重做 |

## 4. 目标架构

（见会话中的架构图：应用 → 系统代理 → Proxira 桌面应用〔MITM 引擎 + 现有 Hono 内核〕→ 上游）

### 三个关键设计决定

**决定一：Electron 主进程内嵌 Hono，窗口直接加载 `http://127.0.0.1:<固定端口>/_proxira/ui`。**
理由：面板、SSE、API 全部零改动，改动面最小。代价是主进程要多扛一个 HTTP server，可接受。

**决定二：MITM 层做成独立中间件，不引入第三方 MITM 代理。**
理由：Proxira 的价值集中在 `ProxyService`（规则 / 重放 / 脱敏 / 历史）。`node-mitmproxy`、`node-http-mitm-proxy` 这类库自带一套代理与请求模型，接进来会把现有管线架空。
做法：MITM 层只负责「把 TLS 流变成 Web 标准 `Request`」，然后喂给现有 `app.fetch`。

**决定三：两种入口并存，互不干扰。**

| 模式 | 触发方式 | 使用者 |
|---|---|---|
| 前缀模式（现状） | 请求打到 `/proxira/*` | CLI / 手动把 SDK baseURL 指过来 |
| 系统代理模式（新增） | 绝对 URI 请求 + `CONNECT` 方法 | 桌面版主入口 |

面板必须显式展示「当前模式」，两种模式产生的记录也要打标区分。

## 5. 关键技术方案

### 5.1 系统代理开关（macOS）

**命令**

```
networksetup -listallnetworkservices                                  # 枚举服务名
networksetup -setwebproxy        <service> 127.0.0.1 <port>
networksetup -setsecurewebproxy  <service> 127.0.0.1 <port>
networksetup -setwebproxystate        <service> off
networksetup -setsecurewebproxystate  <service> off
networksetup -setproxybypassdomains   <service> 127.0.0.1 localhost
```

注意：服务名不一定是 `Wi-Fi`（可能是 `AX88179A` 之类），**必须枚举并对所有 enabled 的服务生效**。

**权限**

`man networksetup` 明确写了改网络设置需要 admin 权限。因为自用且不签名，方案只有一条：

```
osascript -e 'do shell script "<networksetup …>" with administrator privileges'
```

弹系统原生授权框，无需签名，实现简单；代价是**每次开关都会弹密码**。

> SMAppService 特权 helper（授权一次长期有效）需要 app 已签名 + 公证，**在自用前提下不可用**，从方案中去掉。

**还原是硬要求**。因为根 CA 装进 System keychain 且代理是系统级设置，残留配置会把本机搞断网。三重兜底：

1. 正常退出：`app.on('before-quit')` 里先还原系统代理再退
2. 信号退出：监听 `SIGINT` / `SIGTERM`
3. **异常退出（被 kill / 崩溃）**：启动时读 `<数据目录>/proxy-state.json`，若上次状态是「开启」且当前进程不是正常退出 → 先还原再继续启动

同时必须：

- **记录原始配置**：开启前把 `networksetup -getwebproxy` 等的原值存进 `proxy-state.json`，还原时写回原值（不能无脑关掉，万一你本来就有代理）
- **面板自身必须 bypass**：`127.0.0.1` / `localhost` 走 bypass 列表，否则面板请求会打回自己造成死循环
- 提供独立的 `proxira panic` 命令，最坏情况下手敲一条命令恢复网络

### 5.2 根 CA 生命周期

**生成（一次）**

- 存 `<数据目录>/certs/rootCA.key` + `rootCA.crt`
- 扩展：`basicConstraints: CA:true, pathLen:0`、`keyUsage: keyCertSign, cRLSign`
- 有效期 10 年；RSA 2048 或 ECDSA P-256

⚠️ 现有 `gen-cert` 生成的证书**不能**直接当 CA 用（缺 CA 扩展）。需要新增 `gen-ca` 子命令，或给 `gen-cert` 加 `--ca` 开关。

**安装信任**（已定：System keychain，全机生效）

```
sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain <ca.crt>
```

- 通过 osascript 提权执行，与 §5.1 共用同一套提权封装
- 首次安装时 UI 必须明确告知「此证书对全机生效」，并说明它做了什么

**检测与卸载**

- 检测：用 `security verify-cert` 或拿 CA 校验一个测试叶证书，判断是否已受信任
- 卸载：`security delete-certificate -c "<CA CN>" /Library/Keychains/System.keychain` + UI 上一键清理入口
- **注意 Firefox 使用独立信任库**，不受系统信任影响，需要单独说明

### 5.3 HTTPS MITM 内核

**数据流**

1. `http.createServer` 监听 **`connect` 事件**（`CONNECT host:443 HTTP/1.1`）
2. 解析目标 `host:port`，按「拦截范围」分流：
   - **命中直通名单**（证书固定的服务、`*.apple.com` 等）→ 建裸 TCP 隧道到上游，只记录元数据（域名 / 时长 / 字节数），**不解密**
   - **命中拦截名单** → 继续第 3 步
3. 回 `HTTP/1.1 200 Connection Established` 给客户端
4. 用 `tls.createServer({ SNICallback })` 包住这条 socket。`SNICallback` 按 SNI 域名取证书：
   - 内存 LRU 缓存 → 磁盘缓存 `<数据目录>/certs/leaf/<host>.pem`
   - 未命中则用根 CA 私钥现签：`CN=<host>` + `subjectAltName: DNS:<host>` + `basicConstraints: CA:false` + `extKeyUsage: serverAuth`，有效期 1 年
5. 解密后的请求**构造成 Web 标准 `Request`**，喂给现有 `app.fetch`
6. 上游方向用 `http`/`https` 模块**直连目标**（不再走系统代理，避免死循环），响应转成 Web `Response` 交回现有管线

**证书生成手段**

| 方案 | 说明 |
|---|---|
| `selfsigned` v5 | 走 Node 原生 WebCrypto，支持 `ca: { key, cert }` 签发下级证书，依赖最少。**建议先用它做 spike** |
| `node-forge` | MITM 生态最主流（`node-mitmproxy` / `node-http-mitm-proxy` 都用它），扩展表达力最强，但体积与维护状况一般 |

建议：spike 用 `selfsigned`，若 SAN / 扩展表达力不足再换 `node-forge`。

**必须处理的问题**

| 问题 | 说明与对策 |
|---|---|
| ~~HTTP/2~~ | **已决定 v1 只支持 http/1.1**，不做 h2 协商，问题消除 |
| **QUIC / HTTP/3** | 走 UDP，系统代理管不到。Chrome 会对支持 h3 的站点走 QUIC 绕过代理 → 表现为「某些站点抓不到」。自用可在 Chrome 里关掉 QUIC，或用 `--disable-quic` 启动 |
| **证书固定（pinning）** | 部分 App / 服务端固定证书，解密后握手直接失败。**必须支持按域名直通**，并在面板上明确提示「该域名未解密」，否则会误当成 bug |
| **WebSocket / Upgrade** | 现有管线已支持 SSE 透传，MITM 后要保证 `Upgrade` 请求同样透传 |
| **性能** | 全量解密 + 落盘会放大开销。复用现有 `maxBodyCaptureBytes`（2MB）与落盘截断（64KB），再新增「按域名采样」开关 |

### 5.4 桌面壳

**主进程职责**：内嵌 Hono server、窗口、托盘、系统代理开关、CA 管理、退出兜底。

- **窗口**：`BrowserWindow` 加载 `http://127.0.0.1:<port>/_proxira/ui`；macOS 用 `titleBarStyle: 'hiddenInset'` 贴合原生外观
- **单实例**：用 `app.requestSingleInstanceLock()`；保留 `instance.json` 作为双入口（CLI + 桌面）互斥提示
- **端口策略改造**：默认固定 `8899`。被占用时**不再提问**，改为在主进程内换一个空闲端口，并把实际端口同时写进窗口 URL 与系统代理设置——用户无感。同时删掉桌面路径上的 `askForPort()` 调用
- **托盘**：显示当前状态（拦截中 / 已暂停）、请求计数、一键暂停；退出前先还原系统代理
- **崩溃兜底**：`proxy-state.json` + 启动自检（见 §5.1）

### 5.5 打包（自用级）

因为不分发，这块工作量很小：

- `electron-builder` 出 arm64 的 `dmg` 或直接 `app` 目录
- 用 ad-hoc 签名（`codesign -s -`）或干脆不签，首次打开右键「打开」即可
- **不需要** Apple 账号、公证、自动更新框架
- 更简的做法：直接 `pnpm --filter @proxira/desktop dev` 从源码跑，需要「双击启动」时再打包

### 5.6 容易被忽略但一定会挨骂：终端工具不读系统代理

`curl` / `git` / `npm` / 多数 Node 与 Python SDK **不会读取 macOS 系统代理**，只认 `http_proxy` / `https_proxy` 环境变量。而 Proxira 的核心场景恰恰是「调试本地跑的 SDK 请求」——开关打开后发现终端里还是抓不到，必然踩到。

方案（建议 a + b）：

- **a.** 提供 `proxira on` / `proxira off` / `proxira env`，用户用 `eval "$(proxira env)"` 只影响当前 shell
- **b.** 面板上放一张「终端还需要这一步」引导卡片，一键复制 export 命令
- **c.** 可选 shell 注入（改用户 rc 文件）—— 自用可以自己动手，但不做进产品

### 5.7 按进程（App）视角：能做到哪一步

先说结论：**归属能做，作用域做不到，协议覆盖比直觉窄得多。** 这三件事经常被混成一句话，必须拆开。

#### 5.7.1 三个被混在一起的问题

| 问题 | 本质 | 结论 |
|---|---|---|
| 这条请求是哪个 App 发的？ | **归属** | 可解，需额外查表 |
| 这个协议的**内容**能不能看？ | **解密** | HTTP 类可解，裸 TCP / UDP 不可解 |
| 能不能**只**拦某个 App？ | **作用域** | **做不到**，只能全机接管后内部分流 |

#### 5.7.2 归属：源端口反查 PID（可做）

HTTP 协议里**没有任何字段标识发起进程**——代理看到的所有连接都来自 `127.0.0.1`。Charles 和 Proxyman 能"按 App 分类"，靠的是同一台机器上可以反查：

```
客户端建立连接 → 代理 accept，拿到 socket.remotePort（客户端临时源端口，如 54321）
             → 查「端口 → PID」表 → 得到 PID 4711
             → PID → 进程名 / .app bundle
```

Charles 官方文档自认一个细节：Client Process 工具「会在接受每个连接前引入一小段延迟」——那正是这个反查的开销。

三种实现方式：

| 方式 | 做法 | 延迟 | 漏判 |
|---|---|---|---|
| 逐连接查 | 每个新连接跑一次 `lsof -nP -iTCP:<port>` | 每次 20~80ms | 几乎不漏 |
| 定时快照 | 每 1~2s 跑一次 `lsof -nP -i` 全量，建内存映射表 | 无（查内存） | 短连接可能漏 |
| 原生查询 | `proc_pidinfo` / `sysctl net.inet.tcp.pcblist_n`（需 N-API 原生模块） | 无 | 最少 |

**建议**：定时快照为主（1s）+ 逐连接查为兜底（仅当快照未命中）。纯 Node 即可，无需原生模块。

两个必须知道的限制：

- **权限**：`lsof` 只能看到**同 UID 进程**的 socket。你自己的 App（浏览器 / 微信 / curl / node）跑的都是你的 UID → **无需提权即可看到**。root 守护进程看不到，但不是重点。
- **竞态**：端口会被复用，快照最长有 1~2s 滞后，极端情况会张冠李戴。必须允许「未知」这个结果，不能硬猜。

#### 5.7.3 作用域：没法"只拦某个 App"（架构纠正）

这是最容易误解的一点。**系统代理是全局开关**，打开就全机生效，不存在"只把这个 App 的流量交给我"这个选项。

正确的心智模型：

```
全机接管  →  在代理内部按 PID 决定「这条怎么处理」
```

好消息：这和「全机观测」在实现上几乎没有区别——反正都要全机接管。所以「按进程」在 Proxira 里的正确形态不是**拦截开关**，而是**三个维度的能力**：

| 维度 | 形态 | 归属版本 |
|---|---|---|
| 视图 | 左侧列表可按 App 分组 / 过滤，每条记录带 App 归属 | v1（便宜） |
| 诊断 | 显示「该 App 有 N 条连接**绕过**了代理」 | v1（价值最高，见 5.7.5） |
| 规则 | `ProxyRule` 增加 `appProcess` 匹配维度（mock / delay 只对某 App 生效） | v1.5 |
| 解密范围 | 按 App 决定是否 MITM（不值得解密的直接隧道透传） | v1.5（省 CPU 的关键） |

#### 5.7.4 协议覆盖：一张必须钉死的表

| 协议 | 元数据（对端 / 字节数 / 时长） | 内容 | 前置条件 |
|---|---|---|---|
| HTTP/1.1 | ✅ | ✅ | 走系统代理 |
| HTTPS | ✅ | ✅ | 走系统代理 + 装根 CA + **无证书固定** |
| SSE | ✅ | ✅ | 同 HTTPS（它就是 HTTP） |
| WebSocket | ✅ | ⚠️ **要新增工作** | 走系统代理 + 需解析 WS 帧（现有管线只透传，不解帧） |
| 裸 TCP | ✅ | ❌ | 非 HTTP 流量不经过代理，只能靠 `lsof` 拿元数据 |
| UDP | ⚠️ 仅 `lsof` 元数据 | ❌ | 系统代理是 TCP 的，UDP 完全不经过 |

**「看到裸 TCP / UDP 的内容」需要为每个协议写解析器——这是没有边界的工作量，不做。** 要看包内容正确工具是 Wireshark，Proxira 不替代它。

> UDP 补充：DNS 与 QUIC（HTTP/3）都走 UDP，系统代理对它们无效。Chrome 会对支持 h3 的站点走 QUIC 绕过代理——这也是 §5.3 已列的问题。

#### 5.7.5 微信这个具体例子：做不到，且原因是密码学的

必须直说：**「选中微信 → 看到它的传输内容」在当前方案下不可达**。不是难，是不成立。三层原因，任一层单独都足以挡住：

1. **它不走系统代理。** 微信桌面版用自研网络栈（`libcurl` + 自写 TLS 层），底层直接建 TLS 连接，不读 `NSURLSession` / 系统代理配置 / `http_proxy` 环境变量。**在代理进程里连这条连接都看不到。**
2. **证书固定 + 自研协议 MMTLS。** 微信传输用 MMTLS（TLS 1.3 的变体，去掉了客户端认证），服务端身份**不靠 CA 链校验，而靠预置在客户端的 ECDSA 公钥指纹**。这意味着：**你装任何根 CA 都无法冒充微信服务器**——不存在一个它能接受的证书。这是密码学层面的死路，不是配置问题。
3. **主动探测代理。** 新版微信会探测本地代理端口特征、校验系统代理一致性，触发风控后降级为直连。

要突破只有改二进制（Frida hook 掉证书校验、关闭 SIP）这类逆向手段。**这超出 Proxira 的定位**——它是开发联调工具，不是逆向工具，不做进计划。

**但有一个可达的替代**：微信**网页版**（浏览器里打开的 `wx.qq.com`）走标准 HTTPS，**能正常抓到并解密**。调试网页版 / 浏览器里的小程序请求时 Proxira 可用；桌面客户端的私有协议不行。

#### 5.7.6 这件事对产品反而很有价值：把「抓不到」变成可见的诊断

用户最容易困惑的不是"怎么抓"，而是"**为什么抓不到**"。而按进程归属恰好解决这个——因为在 `lsof` 的元数据里，**你能看到那些"没经过代理"的连接**：

```
面板可以显示：
  微信  (PID 4711) → 14 条 TCP 连接，全部绕过代理，未解密
  浏览器 (PID 8899) → 32 条请求，已解密
```

这条能力**不需要 MITM、不需要根 CA、不需要提权**（同 UID 即可），却把最让人抓狂的一类问题（"开关都开了怎么还是抓不到"）从猜谜变成结论。

**建议优先级高于「按 App 解密开关」**，因为它是纯增益、无风险，而后者要动 MITM 分流逻辑。

## 6. 分期与验收标准

### Phase 0 — 技术验证（spike，不做产品化）

- **内容**：① 用 `selfsigned` 生成根 CA + 按域名签发叶证书；② 起一个最小 CONNECT 代理，`curl -x` 走它访问 HTTPS 站点并打印明文；③ 用 osascript 提权跑一次 networksetup 开关并成功还原
- **验收**：`curl -x http://127.0.0.1:8899 https://example.com -v` 能在代理侧看到完整明文响应；系统代理开 → 关之后 `networksetup -getwebproxy Wi-Fi` 与原始配置完全一致
- **产出**：spike 结论（证书库选型、osascript 授权次数是否可接受）

### Phase 1 — 桌面壳 + 内核复用（不含 MITM）

- **内容**：Electron 主进程内嵌 Hono、窗口加载现有面板、托盘、固定端口策略、单实例、退出兜底
- **验收**：`pnpm dev` 能起 Electron 窗口并看到现有面板；关窗后进程干净退出；端口被占用时自动换端口且面板正常

### Phase 1.5 — 按 App 视图 + 「绕过代理」诊断（不依赖 MITM，价值最高）

- **内容**：端口 → PID 快照表（`lsof` 每 1s 一次 + 未命中时逐连接查）、PID → App bundle 解析、记录挂 `appProcess` 归属、左侧列表按 App 分组/过滤、**「该 App 有 N 条连接未经代理」诊断面板**
- **验收**：面板能正确把记录归属到 Chrome / curl / node；打开微信后能看到它的 TCP 连接条数与对端，并明确标注「未经过代理、未解密」；归属失败时显示「未知」而不是猜
- **为什么排在 MITM 之前**：它不需要根 CA、不需要提权、不碰 MITM 内核，却能独立交付「知道谁在说话」这一半价值，并让后续 MITM 的调试有依据

### Phase 2 — 系统代理开关 + 拦截范围

- **内容**：networksetup 开关、三重还原兜底、`proxy-state.json`、bypass 列表、按域名直通/拦截配置、面板上的开关与状态
- **验收**：打开开关后 `networksetup -getwebproxy` 指向 `127.0.0.1:8899`；面板能收到 HTTP 请求记录；**强制 kill 进程后重启，系统代理被自动还原，不残留死配置**

### Phase 3 — HTTPS MITM 接入现有管线

- **内容**：CONNECT + `SNICallback` + 叶证书缓存 + 解密后喂给 `app.fetch`；HTTPS 下规则 / 重放 / 脱敏 / 历史全部生效；pinning 失败的可视化提示
- **验收**：Chrome 访问 `https://api.deepseek.com` 时面板能看到**完整请求头与响应正文**；给某域名加一条 mock 规则后 HTTPS 请求真的被 mock；重放该请求成功；脱敏开关对 HTTPS 同样生效

### Phase 4 — 根 CA 引导 + 一键卸载

- **内容**：首次启动向导（生成 CA → 提权装进 System keychain → 校验信任 → 失败兜底指引）、卸载入口、Firefox 说明
- **验收**：从启动应用到看见 HTTPS 明文，全程只需点几次「授权」并输入一次系统密码

### Phase 5 — 打包（自用级，工作量很小）

- **内容**：electron-builder 出 dmg、图标、ad-hoc 签名
- **验收**：双击 dmg 装好后能启动，首次打开可绕过 Gatekeeper，能正常拦截 HTTPS

## 7. 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| networksetup 每次弹管理员授权 | 高频开关会觉得烦 | 自用场景可接受；可加「保持开启直到手动关闭」减少切换次数 |
| **退出/崩溃残留系统代理设置** | **本机断网，最严重** | 三重还原兜底 + 启动自检 + 独立 `proxira panic` 命令 |
| 根 CA 装进 System keychain 对全机生效 | 卸载不干净会留下受信任的根证书（安全隐患） | 卸载路径必须有测试覆盖；UI 明确显示「已安装/未安装」状态 |
| 证书固定 / QUIC 导致部分站点抓不到 | 误判为 bug | 按域名直通 + 面板显式提示「该域名未解密」+ 文档说明 QUIC |
| App 完全不走系统代理（微信类） | 用户以为工具坏了 | §5.7.5 的能力边界写进面板与文档；用「绕过代理诊断」（Phase 1.5）把它变成可见结论 |
| 端口 → PID 反查的竞态（端口复用、快照滞后） | 归属张冠李戴 | 允许「未知」结果，不硬猜；快照 1s + 逐连接兜底；面板对低置信度归属做弱化显示 |
| 解密后规则语义变化（host 参与匹配） | 现有规则可能误命中 | 规则匹配补 host 维度，保持默认「路径包含」向后兼容 |
| 全量解密放大 CPU / 内存 | 拖慢本机 | 按域名采样、复用 2MB 上限、必要时只记 header 不记 body |
| 两种入口语义混淆 | 不知道请求走哪 | 面板展示当前模式，两种模式的记录打标区分 |
| 仓库是 public，桌面版代码会公开可见 | 个人工具暴露在公开仓库 | 见 §9 第 2 条；如需隐藏则要单独私有仓 |

- `networksetup -setwebproxy` 在「当前用户属于 admin 组」时是否仍需显式提权（man page 说需要 admin；系统设置里若勾了「需要管理员密码才能访问系统级偏好设置」则需 root）
- `security add-trusted-cert` 写入 System keychain 的提权方式与是否需要重启相关服务才生效
- `selfsigned` 对 `subjectAltName` + `basicConstraints: CA:false` 的表达能力是否满足叶证书需求
- Node 的 `http.createServer` 在 `connect` 事件里接管 socket 后，与 `tls.createServer({ SNICallback })` 组合的稳定性（这是 MITM 的核心机制，必须最先验证）
- **端口 → PID 反查的实测准确率与延迟**：`lsof` 快照间隔 1s 时的漏判率、逐连接查的单次耗时、`socket.remotePort` 在 Node 里能否稳定拿到；以及是否真的无需提权就能看到同 UID 全部 App（§5.7.2 的地基）
- 微信是否真的完全不经过系统代理（成本极低的验证：打开系统代理后看面板里有无它的记录）——验完再决定要不要在面板上做「绕过」提示
